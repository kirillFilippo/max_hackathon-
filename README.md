# Ассистент организатора досуга в MAX

Бот в мессенджере **MAX**, который убирает ручную координацию небольших событий:
собирает заявки по одной ссылке, ведёт состав и лист ожидания, задаёт участникам одни
и те же вопросы, напоминает о встрече и держит общий список покупок, чтобы одну позицию
не купили дважды.

- **Платформа:** MAX Bot API (`@maxhub/max-bot-api`), long polling или webhook.
- **Состояние:** PostgreSQL; при обрыве связи бот продолжает работать из памяти
  и переносит данные в базу после восстановления.
- **Мини-приложение:** конструктор вопросов и анкета участника — тот же процесс,
  тот же порт, что и вебхук.
- **Проверено:** 259 автотестов, включая интеграционные на настоящем PostgreSQL.

---

## Проблема и ценность

Организатор небольшого события тратит 1–3 часа на ручную координацию: собирает
подтверждения в разных чатах, задаёт каждому одни и те же вопросы, вручную напоминает
о дате и месте, теряет тех, кто не подтвердил. В походе или на дне рождения к этому
добавляется общий список покупок: кто что берёт и не купили ли одно и то же дважды.

| Было | Стало |
|---|---|
| Сообщение в 2–3 чата, часть людей не увидела | Одна ссылка `max.ru/<бот>?start=ev_КОД` — человек записывается сам |
| Организатор по очереди спрашивает «идёшь?», «во сколько?», «что взять?» | Анкета при регистрации: в чате по шагам или в мини-приложении одним экраном |
| Состав считается в голове | Панель `/events`: идут / под вопросом / не идут / лист ожидания, ответы и контакты |
| Мест 8, записались 11 — разбираются в чате | Бот держит лимит и лист ожидания, поднимает следующего при отказе |
| Напоминания вручную, по нескольку раз | Автоматически: за 48 ч — подтверждение, за час — детали с картой |
| «Я куплю уголь» ×3, вода забыта | Список покупок: позицию бронирует ровно один человек |
| Перенос или смена адреса — рассылка вручную | «Изменить» → участникам уходит, что именно поменялось |

**Одна фраза:** координация живёт в боте, организатор только принимает решения.

## Что умеет бот

| Возможность | Как выглядит |
|---|---|
| Создание события | `/new`: название, дата (`завтра в 11:00`, `25.10 18:30`, `25 октября 19:00`), адрес с подтверждением, описание, лимит, вопросы участникам |
| Ссылка-приглашение | `https://max.ru/<ник_бота>?start=ev_<КОД>`; можно просто отправить код боту |
| Регистрация | имя из профиля MAX, контакт кнопкой или текстом, статус «Иду / Под вопросом / Не смогу» |
| Вопросы участникам | пять типов (текст, число, выбор, да/нет, дата), до 10 вопросов; ограничения как в формах: границы числа, длина текста, один или несколько вариантов, обязательность |
| Мини-приложение | конструктор анкеты списком и форма ответов; включается автоматически для тяжёлой анкеты (вес ≥ 10) или вручную |
| Шаблоны | свои наборы вопросов плюс готовые: настольная игра, день рождения, встреча, спорт, поход |
| Лимит и лист ожидания | при переполнении — лист ожидания; освободилось место — бот поднимает первого и пишет ему |
| Напоминания | за 48 часов подтверждение кнопками, за час — детали, адрес-ссылка на карту и свободные позиции списка |
| Список покупок | позиции добавляет организатор, участники бронируют кнопкой или сообщением `1 3 5`; отказ освобождает позицию |
| Панель организатора | `/events`: состав по статусам, ответы, «Напомнить сейчас», «Изменить», «Завершить событие» |
| Профиль | имя и ник из MAX, контакт для связи (`/profile`) |
| FAQ | `/faq` или свободный текст по ключевым словам в контексте события |

Команды: `/start`, `/new`, `/events`, `/templates`, `/join`, `/profile`, `/faq`, `/help`, `/cancel`.

## Быстрый старт

### Docker (одна команда)

```bash
cp .env.example .env      # укажите BOT_TOKEN
docker compose up --build
```

Поднимаются два сервиса: `postgres` (данные на volume `pgdata`) и `bot`.
Токен можно передать и без файла: `BOT_TOKEN=<токен> docker compose up --build`.

Занятые порты на хосте выносятся отдельно и не мешают портам внутри контейнера:
`MINIAPP_HOST_PORT=18090`, `WEBHOOK_HOST_PORT=18080`.

### Локально (Node.js ≥ 20.19)

```bash
docker compose up -d postgres   # только база
cp .env.example .env            # BOT_TOKEN и DATABASE_URL
npm install
npm run dev                     # или: npm run build && npm start
```

Схема БД приводится к актуальной версии при старте бота (миграции в `src/db/migrations.ts`).

### Проверка в MAX

1. `/start` → «Создать событие» (или `/new`): название → дата → адрес (бот покажет
   экран «Проверьте адрес» со ссылкой на карту) → описание → лимит → вопросы.
2. Бот публикует событие, показывает код (например `A7K2Q`) и ссылку-приглашение.
3. Отправьте ссылку участникам — они записываются, организатор получает уведомление.
4. `/events` → событие: состав, список покупок, напоминания, изменения, закрытие.
5. Адреса и ответы людей никуда не отправляются: единственные внешние точки —
   MAX и ссылки на Яндекс.Карты.

## Архитектура

```
MAX (клиенты организатора и участников)
        │  Bot API: long polling / webhook, диплинки
        ▼
┌───────────────────────────────────────────────────────────┐
│                     ОДИН ПРОЦЕСС                          │
│  bot/       роутеры → мастера (FSM) → разделы             │
│             тексты и клавиатуры, notifier, планировщик    │
│  miniapp/   HTTP на том же порту: конструктор и анкета,   │
│             проверка подписи запуска                      │
│  services/  правила: лимит, лист ожидания, брони, шаблоны │
│  db/        PostgreSQL + зеркало в памяти, миграции       │
│  domain/    чистые функции: даты и TZ, адрес, валидация   │
└───────────────────────────────────────────────────────────┘
```

- **Один процесс, два канала.** Чат и мини-приложение обслуживает один серверный код,
  поэтому правила не расходятся.
- **Зависимости в одну сторону:** `bot → services → db → domain`. Домен не знает
  ни про MAX, ни про SQL — тестируется без сети и SDK.
- **Сервисы меняют состояние, бот отвечает за текст.** Сервис напоминаний возвращает
  задачи «кому и что», рендер и доставку делает слой бота.
- **Инварианты держит база:** `reservations.item_id` — первичный ключ (одна позиция —
  одна бронь), коды событий уникальны, регистрация идемпотентна через `ON CONFLICT`.
- **Критические секции** (`src/db/locks.ts`) — по событию: решения о лимите мест,
  листе ожидания и нумерации позиций зависят от предыдущего чтения.
- **Отказоустойчивость:** при обрыве связи запросы идут из зеркала в памяти, снимок
  состояния пишется на диск, после восстановления данные уезжают в базу с теми же
  идентификаторами.

### Состав каталогов

```
src/
  index.ts        точка входа, graceful shutdown, работа с CA-сертификатом
  app.ts          сборка зависимостей, polling/webhook, планировщик напоминаний
  config.ts       переменные окружения и их проверка
  logger.ts       логи с уровнями и разворачиванием цепочки cause
  domain/         типы, даты и часовые пояса, адрес и карты, вопросы, статистика
  services/       profile, event, participant, item, template, faq, reminder, debug
  db/             пул, миграции, репозитории (PostgreSQL и память), resilient-режим
  bot/            роутеры, мастера, экраны, тексты, дедупликация, доставка
  miniapp/        HTTP-сервер мини-приложения: страницы и API, проверка подписи
test/             домен, сценарии бота целиком, контракт репозиториев, работа без
                  базы, HTTP мини-приложения — на настоящем PostgreSQL
```

### База данных

| Таблица | Что хранит |
|---|---|
| `users` | профиль: имя, ник, контакт для связи |
| `events` | код (UNIQUE), дата, адрес и координаты, лимит, вопросы (jsonb), режим анкеты, статус |
| `participants` | заявки: статус, ответы (jsonb), лист ожидания, отметки напоминаний |
| `event_items` | позиции списка покупок |
| `reservations` | брони: `item_id` — первичный ключ, поэтому позиция ровно у одного человека |
| `templates` | наборы вопросов организатора |
| `sessions` | черновики мастеров и подписи конструктора с TTL |

Полезные команды:

```bash
docker compose exec postgres psql -U dosug -d dosug -c '\dt'      # список таблиц
docker compose exec postgres pg_dump -U dosug dosug > backup.sql  # резервная копия
```

## Напоминания

Планировщик просыпается каждые `REMINDER_TICK_SECONDS`:

| Окно | Кому | Что отправляет |
|---|---|---|
| `[начало − 48 ч, начало − 1 ч)` | всем, кроме «не иду» | «Подтвердите участие» с кнопками статуса |
| `[начало − 1 ч, начало)` | всем, кроме «не иду» | детали: дата, адрес-ссылка на карту, кто идёт, свободные позиции |
| `начало + 3 ч` | — | событие закрывается автоматически |

Напоминание уходит ровно один раз (отметка хранится у участника), при сбое доставки
повторяется на следующем тике, после перезапуска бота не дублируется. Для события,
созданного уже внутри окна, подтверждение не рассылается — чтобы не спамить.

Для демонстрации удобно поставить `REMINDER_CONFIRM_HOURS=1`,
`REMINDER_FINAL_HOURS=0.05` и `REMINDER_TICK_SECONDS=15`.

## Работа без базы

`STORAGE_MODE=auto` (по умолчанию) рассчитан на схему «один бот + одна база»:

1. первый неудачный запрос помечает соединение потерянным и пишет причину в лог;
2. дальше запросы обслуживает зеркало в памяти — события, заявки и брони продолжают
   работать, а пользователь не видит ошибок;
3. раз в `STORAGE_CHECK_SECONDS` сторож проверяет базу и напоминает в лог, сколько
   данных ждёт синхронизации;
4. пока связи нет, снимок памяти пишется в `OFFLINE_STATE_PATH`, поэтому перезапуск
   контейнера данные не теряет;
5. когда база вернулась — применяются миграции, накопленное переносится в PostgreSQL
   с теми же идентификаторами, черновики мастеров уезжают в таблицу сессий.

`GET /health` показывает режим и состояние: `{"ok":true,"storage":{"mode":"memory",…},
"db":{"online":false,"lastError":"…"}}`. По нему видно, что бот жив, даже когда база
недоступна.

## Отладочные данные

Команды включаются переменной `DEBUG_COMMANDS=1`:

- `/debugcreateevent` — создаёт событие от имени вызывающего и наполняет его:
  девять участников (идут, под вопросом, не идут, лист ожидания), ответы и список
  покупок с бронями. Удобно проверять панель организатора и покупки.
- `/debugreceiveevent` — создаёт событие «чужого» организатора и записывает
  вызывающего участником: видно путь участника.

Синтетические люди помечены отрицательными id — сообщения им не отправляются.
Команды создают реальные записи, поэтому в проде их держат выключенными.

## Сертификаты

MAX API (`platform-api2.max.ru`) не проходит проверку системным хранилищем Node:
корневой сертификат Russian Trusted Root CA (Минцифры) в него не входит. Поэтому
сертификат лежит в репозитории (`certs/`) и копируется в образ — в `Dockerfile` задан
`NODE_EXTRA_CA_CERTS`, и бот работает сразу после сборки.

Если сертификат есть, а переменная не выставлена (запуск без Docker), бот сам
перезапускается с `NODE_EXTRA_CA_CERTS` — Node читает эту переменную только при старте.
Свой сертификат можно указать через `MAX_CA_CERT_PATH`.

## Разработка

```bash
npm run dev         # tsx watch src/index.ts
npm run typecheck   # tsc --noEmit
npm test            # 259 тестов, включая интеграционные на настоящем PostgreSQL
npm run build       # сборка в dist
npm run verify      # typecheck + тесты + сборка
```

Тесты поднимают **настоящий PostgreSQL** (`embedded-postgres`) и применяют те же
миграции, что и в проде, поэтому проверяется реальный SQL, а не мок. Сетевых тестов
к MAX нет: основной сценарий проверяется вручную по разделу «Проверка в MAX».

## Остановка и резервные копии

```bash
docker compose down                         # остановить
docker compose exec postgres pg_dump -U dosug dosug > backup.sql   # копия
cat backup.sql | docker compose exec -T postgres psql -U dosug -d dosug  # восстановить
```

Данные лежат на volume `pgdata`, поэтому переживают перезапуск, пересборку образа
и обновление кода. Снимок `OFFLINE_STATE_PATH` нужен только на время обрыва связи
и удаляется после успешной синхронизации.

## Ограничения и допущения

1. **Long polling по умолчанию.** Удобно для проверки, но платформа рекомендует webhook
   для production; режим `BOT_MODE=webhook` поддержан (нужен публичный HTTPS).
2. **Один процесс и один инстанс БД.** Решения о составе и нумерация позиций защищены
   очередью в процессе (`src/db/locks.ts`), поэтому несколько реплик потребуют
   блокировок на стороне БД; планировщик напоминаний тоже рассчитан на один процесс.
3. **Нет внешнего геокодера.** Адрес вводится текстом, бот проверяет формат, показывает
   ссылку на Яндекс.Карты и просит организатора подтвердить.
4. **Мини-приложение требует HTTPS** и настройки адреса в кабинете MAX
   (`business.max.ru`). Без `MINIAPP_URL` вопросы и ответы работают в чате.
5. **Режим памяти — для одного процесса:** зеркало живёт в процессе, при нескольких
   репликах нужен общий PostgreSQL (`STORAGE_MODE=postgres`).
6. **Расчётов в продукте нет.** Бот не спрашивает суммы, не делит траты и не передаёт
   реквизиты — это осознанно вынесено за границы версии.

## Возможности расширения

- **Расчёты по общим тратам:** фактические суммы по позициям, доля каждого идущего
  и минимальный список переводов вместо «все должны всем».
- **Обмен реквизитами и закрытие долга:** карточка «вы должны», подтверждение получения.
  Технически это отдельный сервис и таблица запросов на перевод; прежняя схема удалена
  миграцией `0003_drop_settlements`, поэтому возвращать её нужно осознанно.
- **Панель организатора мини-приложением:** таблица участников и список покупок —
  те же сервисы, другой интерфейс.
- **Очередь задач** для рассылок и напоминаний, чтобы запускать несколько реплик.
- **Метрики и трейсинг:** сейчас только логи.
- **Геокодер** для проверки адреса и подсказок.

**Бот не платёжный сервис.** Даже в расширенной версии он только считает и показывает
расклад: деньги участники переводят друг другу сами.
